# Dashboard

A Streamlit app that shows the project's results. It **only reads files**: the result files in
`outputs/` (summaries generated by the `make_*` scripts and the run folders), the replay files
made by `scripts/make_replays.py`, and the detector weights. It contains no result numbers of
its own. Every chart, tile and table has a small **ⓘ source** chip that opens the files it read
and the git commit that last changed each of them.

```bash
pip install -e ".[dashboard]"
streamlit run src/trafficsense/dashboard/app.py
```

Pages:

1. **Overview**: the headline result (ambulance travel time, MaxPressure vs the fastest LLM arm,
   with the pre-registered arm and rule-based preemption beside it), three stat tiles, the project
   in three steps and the system architecture.
2. **Live Detection**: run the IDD-trained YOLOv8n (`best.pt`) on an uploaded video or on the
   bundled sample clip; a player with the boxes, the count per class per frame, and measured speed.
3. **Network Replay**: two saved runs of the 2x2 grid side by side on one clock, drawn on a canvas:
   vehicles, signals, queues, the ambulance and its trail, and each controller's decisions.
4. **Results**: one tab per study, each opening with a one-line takeaway computed from the data,
   then the charts and tables, with their honesty notes.

## Design

Dark "mission control": a near-black page with a faint grid, one accent colour (electric teal) for
the interface, and colours that keep one meaning everywhere: green = good / green light, amber =
the transition (yellow) phase, red = queue / bad, the ambulance red and white. Fonts are Geist and
Geist Mono from Google Fonts (`.streamlit/config.toml`); offline, the browser falls back to its
system fonts. The theme lives in three files that are changed together: `.streamlit/config.toml`
(Streamlit's own widgets), `src/trafficsense/dashboard/assets/theme.css` (everything else, injected
once by `app.py`) and `theme.py` (the same tokens for Python and the shared Plotly template).

* **Data colours** are separate from the interface colours. Controllers keep the dataviz skill's
  validated dark categorical palette (checked again on this page's surface: CVD and normal-vision
  separation and contrast pass). Vehicles on the replay map use composite encoding: each is drawn
  to its own length and width, so size separates two-wheelers, cars and autos, and buses and trucks;
  hue then separates the two of each size class, with pairs that pass the validator all-pairs.
* **Honesty labels** (pre-registered, exploratory, no significance test, post-hoc, hosted) are
  coloured badges next to what they qualify; longer explanations are in each page's "Why / How to
  read" drawer.
* **Count-up and entrance animations** only animate towards the number already on the page (the
  page holds the final text; the script writes it back unchanged) and respect
  `prefers-reduced-motion`.
* **Custom components.** The replay canvas and the detection player are Streamlit components
  (`st.components.v2`, `assets/replay.js` and `assets/player.js`) that get their data as JSON.

## Replays (pre-registered)

*Written and committed before any replay was generated.*

The saved runs store per-step phase and total queue per intersection (`metrics.csv`) and every
LLM decision (`decisions.jsonl`), but not vehicle positions or queues per approach. The replay
page needs those, so a few runs are **replayed** with extra logging:

* **Which runs.** Scenario `indian_2x2_peak_amb` (peak demand with ambulances). The seed is the
  one whose flow file has the most ambulances among the emergency seeds 0–4: a property of the
  demand, not of any result (`docs/emergency.md`: seed 1, 14 ambulances; the script checks the
  rule from the flow files and stops if it picks another seed). Every full-length (3600 s) run
  of that scenario and seed with exact counts: MaxPressure, Webster, MaxPressure + preemption,
  the main LLM arm (`llm_guarded_mp`, `llama3.2:3b`), the exploratory arm
  (`llm_guided_mp_v3`, `gemma4:e4b`), and the model-size study's `llm_guided_mp_v3` runs with
  `qwen2.5:3b`, `llama3.2:3b`, `llama3.1:8b` and Nemotron 3 Ultra (exploratory). The nine run
  folders are listed in `configs/default.yaml` (`dashboard.replays.runs`).
* **No new runs, no LLM calls.** A replay re-drives the simulator with the run's own decisions:
  LLM runs from their `decisions.jsonl` (every applied phase is logged), deterministic
  controllers (MaxPressure, Webster, preemption) by running the same controller again. CityFlow
  is deterministic for a given phase sequence, so the replay is the same run. Re-running an
  LLM run would not be: Ollama on the GPU is not bit-for-bit repeatable (`docs/results.md`).
* **Checked, not assumed.** A replay is kept only if it reproduces the saved run's ATT,
  throughput, queue, waiting time and every ambulance's travel time and stopped time
  exactly; otherwise `scripts/make_replays.py` stops with an error.
* **What is logged** (CityFlow's own replay log plus the env): per step, the phase shown at
  each intersection, waiting vehicles (speed < 0.1 m/s, the queue definition) per approach,
  and the position and type of every vehicle. For deterministic controllers, each request to
  the signal with MaxPressure's pressures at that moment (their decision log).
* **Where.** `paths.replays` (a symlink to D; a few MB per run, not in git). Each replay has a
  `meta.json` with the source run, the sha256 of its `summary.json`, the commit the replay was
  made at, and the verification result.

**As made:** `python scripts/make_replays.py` checked the rule from the flow files (ambulances per seed
0–4: 3, 14, 6, 6, 8, so seed 1) and that the nine listed runs are exactly the eligible ones; all nine
replays reproduced their runs' metrics and all 14 ambulances exactly (about 6 s and 1.5 MiB each).
`--check` verifies that each replay still matches its source run (sha256 of `summary.json`).

## Setup (once)

The replays and the sample clip live on D (not in git), behind gitignored symlinks named in
`configs/default.yaml`:

```bash
ln -s /mnt/d/trafficsense/replays data/external/replays
ln -s /mnt/d/trafficsense/dashboard_media data/external/dashboard_media
python scripts/make_replays.py        # ~1 min, no LLM needed
python scripts/make_sample_clip.py    # needs the IDD symlink (paths.idd_root)
```

Without them the Overview and Results pages still work; the other two pages say which file is
missing and which command makes it.

## Pages in detail

* **Overview.** The headline is the pre-registered LLM arm's ambulance result: `1 − LLM main /
  MaxPressure` for the mean travel time of the signal-relevant ambulances. Beside it, as secondary
  numbers: the exploratory gemma4 hybrid (with its badge) and rule-based preemption. Nothing
  exploratory is the biggest number on a page. The grid animated behind it is a
  schematic, not data (said in the page's drawer). Stat tiles: average travel time of the
  pre-registered arm vs the best baseline, the detector's mAP50 on the IDD test split, and the
  camera-error impact (a fixed plan reads no counts, so it shows "unaffected" rather than +0.0%).
  The three-step story and the architecture diagram follow; the decision interval in the diagram's
  caption is read from `results.json`.
* **Live Detection.** `best.pt` is found from `paths.detector_runs` and `perception.train.run_name`
  and refused unless its sha256 matches the evaluated weights in `detector_test.json`. Default
  confidence: the operating point frozen on validation (`detector_val.json`). Device: the GPU if
  CUDA is available and at least `dashboard.detection.min_free_vram_mib` are free (the LLM and YOLO
  cannot share the GTX 1650), else the CPU; the page says which and why. Before a run the page shows
  the clip's first frame and a filmstrip read from the file. After a run: a player that draws the
  detector's boxes on each frame (class colours; a class can be hidden), the boxes per class in the
  current frame and over all frames, and four measured figures (detector FPS, latency per frame
  with its p95, end-to-end FPS, device), none of them stored. Caveats on the page: IDD is dashcam
  footage; counts are per frame (no tracking); the sample clip is IDD's sampled frames, so it is a
  time-lapse. The sample clip uses the longest evenly spaced frame run of our test split (rule
  checked by the script), first 60 frames at 4 fps.
* **Network Replay.** Two of the nine replays side by side on one clock, over a window that
  defaults to the selected ambulance's trip (at most 600 s are sent to the browser). Ambulances are
  listed by start time (signal-relevant only); the default is the first one, a rule fixed before the
  page was first rendered, not a choice by result (stated on the page). Above the canvas: the
  selected ambulance's travel time in both runs next to the means over all ambulances of the seed
  and over its signal-relevant ones, and each run's ATT.
  The canvas draws, for every second of the window, the positions and headings CityFlow logged at
  the end of that second; between two logged seconds a vehicle moves on the straight line between
  its two logged positions (vehicles that enter or leave fade in or out). Nothing else is invented:
  signal states (the phase shown during the second, from `replay.npz`) and queues (waiting vehicles
  per approach at its end) change only at logged seconds. Drawn per junction: each incoming lane's
  stop line in its signal's colour, the movements of the green (or yellow) phase, a queue bar per
  approach (the same metres per vehicle in both panels) with its count, the phase in the LLM
  prompt's own words (`W+E straight`, `N only`). The selected ambulance is enlarged, flashes, and
  leaves a trail of its logged positions; a timer counts from its scheduled start and stops at the
  travel time in `summary.json`. Views: the whole grid or a camera that follows the ambulance.
  North is up in every view. *As simulated* (the default) draws CityFlow's layout, whose road names
  match the compass. *Keep left* draws the left–right mirror image, which is how this project models
  India's left-hand traffic (`docs/indian_scenario.md`); there east and west swap sides, so the road
  the decision logs and the LLM prompts call E is drawn on the left (the compass says so). The
  default pair is MaxPressure and the pre-registered LLM arm. Under the canvas, both runs' decisions as cards on
  the same clock (the latest one highlighted, ambulance decisions marked): the LLM's own reason, a
  guard override, or MaxPressure's pressures; "Show raw decision data" adds every logged field.
  Below: the network queue over the whole hour for both runs.
* **Results.** Five tabs, each from a results file and each opening with a takeaway sentence
  computed from it: signal control (ATT mean ± std per controller as a dot plot, a paired-by-seed
  slope chart read from the run summaries `results.json` lists, all metrics, LLM decision
  statistics), ambulances (where their time goes: stopped vs the rest of the trip, per controller,
  model-size rows labelled exploratory), model size (labelled exploratory; the split "slower than
  MaxPressure on every seed" / "≈ MaxPressure" is computed from `seeds_worse`, the first model from
  which no model is worse on every seed), camera errors (paired change per level, the
  detection-rate sweep, the post-hoc decomposition as a waterfall per scenario) and the detector
  (mAP50 per class, miss rate by object size). Each tab carries its honesty notes.

## Tests

`tests/test_dashboard.py`:

* **Every number traceable.** Each page is rendered with Streamlit's AppTest. Every number a
  reader can see (HTML blocks without their CSS and scripts, tables, widget options, chart labels
  and hover values, and the custom components' JSON payloads) must equal, at its shown precision, a
  value in one of the files that page read (the data layer records them), or a value the page
  computed from them through `data.derived()` (e.g. a % difference of two means). No allowlist.
* **No hardcoded decimals.** Overview and Results are rendered again from a copy of their data in
  which every float is changed (a factor and offset that depend on its position in the file). A
  decimal number shown unchanged at the same place would not come from the data.
* **Sources.** Every source chip names only files the page read, each with its git state, and
  every results file (`outputs/...`) a page read is named by some chip.
* **The replay is the log.** The replay canvas's payload is decoded and compared with
  `replay.npz` second by second: the same vehicles, positions to 1/20 m, headings, phases and
  queues; the ambulance's times are those in `summary.json`.
* **Per-seed values.** The run summaries behind the slope chart reproduce `results.json`'s paired
  differences exactly.
* **What leads.** The Overview headline is the pre-registered arm's number; every replay view keeps
  north up, the default view is as simulated, and the default pair is MaxPressure and the
  pre-registered arm.

  by hand when the tests were written, and again after the redesign).

## Screenshots

`python scripts/screenshot_dashboard.py` starts the app on a free port and saves every page and
state with Playwright: each page, the Results tabs, Live Detection before and after a run, and the
replay as loaded, mid-playback, following the ambulance, as simulated, and with its notes open. The
1366×768 set goes to `docs/screenshots/` (in git); the 1920×1080 set, checked the same way, to
`<paths.dashboard_media>/screenshots/1920/` (on D, not in git). Chromium needs `libnspr4`, `libnss3` and `libasound2`; without root they can be unpacked from
the Ubuntu packages into a user folder (`apt-get download libnspr4 libnss3 libasound2`,
`dpkg -x <deb> ~/.cache/pw-libs/root`) and passed with
`LD_LIBRARY_PATH=~/.cache/pw-libs/root/usr/lib/x86_64-linux-gnu`.
