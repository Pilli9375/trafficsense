# Indian 2x2 scenario

A 2x2 grid of signalised intersections with an Indian vehicle mix, at two demand levels
(off-peak and peak), used to compare FixedTime and MaxPressure before the LLM controller is
added.

**In short:** the network is generated with CityFlow's own grid generator (200 m spacing,
3.0 m lanes, 3 lanes per direction, 45 km/h). Vehicles are 45% two-wheelers, 18%
auto-rickshaws, 31% cars, 2% buses and 5% trucks, with per-type size and driving parameters.
Demand was calibrated against measured capacity under MaxPressure: off-peak 2375 veh/h
(busiest lane at 0.11–0.13 of its saturation flow) and peak 4750 veh/h (0.21–0.22; the
network stops draining at 5500 veh/h). MaxPressure beats both FixedTime plans at both
levels; at peak FixedTime no longer drains. CityFlow is lane-based, so lane-free driving and
two-wheeler filtering are **not** modelled (next section).

Every table in this document is generated by `scripts/make_indian_tables.py` from
`outputs/indian_2x2/runs/*/summary.json`, `outputs/validation/indian_demand_calibration.json`,
the flow files and `configs/scenarios/indian_2x2.yaml`; `make_indian_tables.py --check` fails
if the document and the data disagree.

## What this scenario can and cannot represent

**CityFlow is a lane-based simulator, so this is not a model of real Indian traffic
behaviour.** In CityFlow every vehicle drives in exactly one lane, follows the vehicle in
front of it (car-following), and changes lane only at discrete moments (and here, not at all:
`lane_change: false`). It has no notion of lateral position inside a lane. It therefore
**cannot** model:

* **non-lane-disciplined driving**: vehicles straddling lanes, using the gaps between lanes,
  or forming more "lanes" than are marked;
* **two-wheelers filtering** between or alongside cars, or queuing two or three abreast at a
  stop line and moving to the front of the queue;
* **width-based interaction**: CityFlow reads a vehicle's `width` but does not use it in the
  dynamics (it is only written to the replay file; checked in CityFlow's source,
  `engine.cpp`/`vehicle.cpp`), so a 0.7 m motorcycle occupies a lane exactly like a 2.4 m bus;
* bicycles, pedestrians, buses stopping at kerbside stops, on-street parking, encroachment,
  U-turns, and wrong-way driving;
* per-type turning speed: CityFlow uses the same turn speed (8.33 m/s) for every vehicle.

What we do model is the **vehicle mix and per-type parameters**: each vehicle type has its own
length, minimum gap, desired time headway, maximum speed, and acceleration and deceleration.
This changes how much space a queue takes, how fast a queue discharges and how fast vehicles
accelerate, but motorcycles still queue in single file like cars. Because of this, the
saturation flows and capacities below are **CityFlow's** for this mix, and are likely
**lower in vehicles per hour** than the same road would carry with real Indian two-wheeler
behaviour. Results from this scenario should be described as "a lane-based simulation with
an Indian vehicle mix", not as a simulation of Indian traffic.

Two further simplifications:

* **Left-hand traffic is represented by mirroring.** India drives on the left; CityFlow's
  generator builds right-hand traffic. A square grid is mirror-symmetric, so a right-hand
  network is the mirror image of a left-hand one, and the simulation is the same with the
  turn labels swapped: CityFlow's `turn_right` (kerb side, allowed in every phase including
  the transition phase) plays the role of India's **free left turn**, and CityFlow's
  `turn_left` (crosses opposing traffic, protected phase) plays the role of India's **right
  turn**. Config, code and output use CityFlow's labels; this document says which is which.
* **Demand is synthetic**: Poisson arrivals with fixed turning probabilities, not counts from
  a real junction. The levels are calibrated against measured capacity (below), not against
  observed Indian traffic volumes.

## Network

Generated by `scripts/generate_indian_roadnet.py` with CityFlow's own grid generator
(`gridToRoadnet`, vendored from CityFlow at commit `5d2ef06`, Apache-2.0) from
`configs/scenarios/indian_2x2.yaml`.

| Parameter | Value | Source / assumption |
|---|---|---|
| Grid | 2 x 2 signalised intersections | Phase 2 specification |
| Spacing between intersections | 200 m | Phase 2 specification |
| Entry / exit road length | 200 m | ASSUMPTION (same as spacing) |
| Lanes per direction | 3: one left, one straight, one right-turn lane | Phase 2 specification (2–3 lanes); one lane per turn is the CityFlow generator's layout |
| Lane width | 3.0 m | Phase 2 specification (~3.0 m) |
| Lane speed limit | 12.5 m/s (45 km/h) | ASSUMPTION within the Phase 2 range of 11–13 m/s |
| Intersection half-width (centre to stop line) | 12 m | ASSUMPTION: covers the 9 m of three 3 m lanes plus 3 m |
| Phases | phase 0 = 5 s transition (right turns only), phases 1–8 green | CityFlow generator (`tlPlan=False`), same layout as the CoLLMLight roadnets; 5 s is not calibrated to Indian amber/all-red practice |
| Signal timing | min green 10 s, max green 60 s, transition 5 s inserted on every switch | `configs/default.yaml` (Phase 1 decisions) |

Lane storage between two stop lines is 200 − 2 × 12 = 176 m, about 38 vehicles of this mix
(176 m / 4.6 m, the share-weighted mean of length + minGap).

The old `data/synthetic/indian_2x2_roadnet.json` had empty `roadLinks`, so no vehicle could
cross an intersection; it is kept in `outputs/_invalid_legacy/` for reference only.

## Demand

`scripts/generate_indian_flow.py --level <offpeak|peak> --seed <n>` writes
`data/scenarios/indian_2x2/flow_<level>_s<n>.json` and a `.meta.json` (vehicle type of every
flow entry, counts, settings). All randomness comes from one `numpy` generator seeded with
the seed, so different seeds give different traffic and the same seed always gives the same
file (tested).

* **Arrivals**: a Poisson process on each of the 8 entry roads over 0–3600 s, floored to whole
  seconds (CityFlow needs integer start times). Each vehicle is its own flow entry.
* **Entry weights** (ASSUMPTION): east–west is the major road (weight 1.0 on each W and E
  entry), north–south the minor road (0.6 on each N and S entry).
* **Turns** (ASSUMPTION), drawn at every intersection the vehicle reaches: straight 0.60,
  free left (CityFlow `turn_right`) 0.25, right (CityFlow `turn_left`) 0.15. A route that would
  come back to an intersection it already passed (circling the block) is redrawn; this shifts
  the realised turn shares by well under 1 percentage point (tested).
* **Vehicle type**: drawn per vehicle from the normalised shares above.

## Capacity and demand calibration

The goal was demand that is realistic for a signalised network: off-peak clearly
undersaturated, peak near capacity with heavy queues but still draining, judged under
MaxPressure. `scripts/calibrate_indian_demand.py` does this in three steps.

### 1. Measured capacity

Measured with the vehicle mix (`trafficsense.sim.capacity`):

<!-- BEGIN:capacity -->
| Quantity (mixed traffic, measured) | veh / h | How |
|---|---|---|
| Saturation flow, straight lane | 2100 | queue discharge, green s 10–70 after 900 s red |
| Saturation flow, protected-turn lane (Indian right turn) | 2040 | same |
| Entry admission limit (CityFlow insertion) | 1341 | permanent green, fed 2 veh/s, minutes 20–60 |
<!-- END:capacity -->

The **saturation flow** is what a green phase can serve: it is the number a signal's capacity
is built on (capacity of a lane ≈ saturation flow × its share of green). The **entry admission
limit** is a CityFlow property: a waiting vehicle is put on an entry lane, at speed 0, only once
the previous vehicle is `length + minGap` ahead, so an entry lane cannot admit more than this
even under a permanent green (see also the correction in `docs/validation.md`, section 2).

### Why the network breaks down at a busiest-lane ratio of only ~0.25

At R* the busiest lane needs only about a quarter of its saturation flow, and Y is about 0.55
(sweep table). Classical signal timing (Webster) puts capacity at roughly
Y ≈ 1 − (share of time lost to transitions), so the early breakdown needed explaining.
`scripts/validation/diagnose_indian_breakdown.py` re-runs MaxPressure at R* with seed 2 (the
seed that failed there) and records where vehicles pile up
(`outputs/validation/indian_breakdown_5500_s2.json`):

<!-- BEGIN:breakdown -->
| t (s) | Vehicles running | Waiting to enter | Incoming lanes at storage (vehicles / storage) |
|---|---|---|---|
| 600 | 281 | 5 | none |
| 1200 | 354 | 10 | none |
| 1800 | 356 | 34 | none |
| 2400 | 365 | 58 | none |
| 3000 | 364 | 146 | none |
| 3600 | 375 | 183 | none |

Time in the transition phase: intersection_1_1 32%, intersection_2_1 33%, intersection_1_2 33%, intersection_2_2 32%. Largest backlogs at 3600 s by first route hop: road_3_2_2 -> road_2_2_2 (82), road_0_1_0 -> road_1_1_0 (82), road_2_0_1 -> road_2_1_1 (19).
<!-- END:breakdown -->

What the data shows:

* **About a third of every intersection's time is transition (lost) time** (32–33%,
  counted from the phase the simulator showed in each step). MaxPressure re-decides every 5 s
  and switches as soon as another phase has more pressure and min green is met, and every
  switch costs 5 s of transition. With a third lost, the usable share is about 0.67.
* **The backlog forms at the major-road entry lanes, with no lane full.** Vehicles waiting
  to enter grow steadily through the hour, while no incoming lane reaches its storage at
  any snapshot. Almost all of the backlog is on the east and west entries going straight.
  **Spillback** (a full downstream lane blocking an upstream intersection) does not occur at
  this demand, so it is not the cause; it does appear at higher demand (e.g. 6000 veh/h and
  above), once the backlog has grown, by running the same script with `--rate 6000`.
* The remaining gap between Y ≈ 0.55 at breakdown and the ≈ 0.67 usable share is consistent
  with MaxPressure not dividing green in Webster's proportions (it reacts to queue pressure
  and uses all 8 phases, including single-approach ones). This last point is **not verified**.

This is a property of the controller as configured (5 s decisions, 5 s transitions), not
just of the network, so the capacity found here is "capacity under MaxPressure", as the
calibration goal asked for. FixedTime has its own, different capacity (see the results).

What the tables show (generated vehicles: 2345 / 2404 / 2430 off-peak and
4667 / 4796 / 4795 peak for seeds 0 / 1 / 2, from the `.meta.json` files):

* **Off-peak is clearly undersaturated for every controller.** No vehicle is left waiting
  to enter, and 95.6–97.7% of generated vehicles finish within the hour; the rest are still
  driving at 3600 s. MaxPressure has the lowest ATT (82.0 s vs 121.5 s for 4-phase
  FixedTime) and 37% of its queue (3.91 vs 10.58 vehicles per intersection).
* **At peak, MaxPressure is near capacity but drains; FixedTime does not.** MaxPressure
  leaves at most 1 vehicle waiting to enter, with queues about 6.6 times its off-peak level.
  Both FixedTime plans leave about 300 vehicles (6–7% of those generated) waiting to enter
  at 3600 s, which fails the 2% backlog criterion used for calibration. Because ATT includes
  time spent waiting to enter, this backlog is a large part of FixedTime's peak ATT
  (279.9 s vs 142.4 s).
* **This difference is partly by construction.** The peak level was calibrated to be near
  capacity *under MaxPressure*, as specified, so it is beyond FixedTime's capacity. The
  peak comparison is therefore between a controller working near its capacity and one
  working beyond it. A level calibrated under FixedTime would be lower and would show a
  smaller gap.
* **MaxPressure wins despite losing more time to transitions**: about 32% of the time,
  vs 14% for FixedTime (5 s per 35 s cycle step). Reacting to queues outweighs the extra
  lost time on this network at both levels.
* **4-phase FixedTime beats 8-phase FixedTime** at both levels (ATT 121.5 vs 129.3 s
  off-peak, 279.9 vs 291.9 s peak), as on Jinan and Hangzhou and unlike Synthetic 4x4
  (`docs/validation.md`, section 3).
* **Seed spread is largest for MaxPressure at peak** (ATT 127.9 to 162.9 s). Near capacity,
  delay grows steeply with small differences in demand: seed 0 is also the seed that took
  longest to empty in the calibration sweep at this demand (470 s vs 236 s and 276 s).
* **Consistency check:** the three peak MaxPressure runs reproduce the calibration sweep's
  4750 veh/h runs exactly (same ATT, throughput and queue to the last digit), as they
  should: same flow files, same controller, same code path.

## Reproducing

```bash
python scripts/generate_indian_roadnet.py
python scripts/calibrate_indian_demand.py --rates 1000 2000 3000 4000 4500 4750 5000 5250 5500 5750 6000 7000 8000 10000 12000 14000
# copy the selected levels into configs/scenarios/indian_2x2.yaml (demand_levels), then
python scripts/generate_indian_flow.py --level all --seed 0 1 2
python scripts/run_indian_experiments.py        # needs a clean git tree
python scripts/validation/diagnose_indian_breakdown.py   # breakdown diagnostic at R*
python scripts/make_indian_tables.py
```
